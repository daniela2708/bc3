# Weis · Promo Effectiveness (UC3 prototype)

A clickable, preliminary prototype of Use Case 3, **Promo Effectiveness**, for Weis Markets. It follows the structure, stack and look of the UC2 Profitability Tracking prototype (and the patterns shared with UC1 and UC5): dark header, disclaimer strip, filter card, a title per view followed by 5–8 key-figure tiles (see Layout rules), hierarchical tables with a column chooser and Excel export, charts with a table view, and a bottom tab bar.

The requirements workbook **UC3_KPIs_Definitions_and_Mapping.xlsx** is the source of truth for views, KPI names, priorities, definitions, calculations, filters and open-question numbers and statuses. Every KPI shown traces to a row of its KPI sheet, except the ones listed with another status in the traceability table below (Total Gross Sales and LY / YoY reuse UC1 definitions; Baseline Sales $ and Baseline Units are kept because the lift KPIs need them, #4) and the items **requested in the prototype review** (marked so in the views and traceability tables): the **Hot Buy Score**, the promo fatigue and discount floor columns, the promotion timing heat map, the Event count row and lift colour thresholds of Promo Run Trend, and the Promo Shopper Impact layout proposals. The Hot Buy Score follows the business method (Weis Hot Buy Scoring Framework, weights pending #19) and the promo hygiene columns use the calibrated thresholds of the Promo Hygiene Review; the lift colour thresholds are still examples. Each is kept in one config file (`src/lib/scoring.ts`, `src/lib/fatigue.ts`, `src/lib/thresholds.ts`), with only the values: no Weis or SymphonyAI document is stored in the repository.

> **Illustrative data only.** Every figure is simulated. Brand and vendor names are real consumer brands used for illustration only; no figure reflects Weis Markets or vendor results. There is no customer, card or employee data. Store and district numbers follow the UC2 structure.

## Run it

```bash
npm install
npm run set-access-password   # once: asks for a password and writes only its salted hash to .env.local
npm run dev                   # http://localhost:5173
npm test                      # Vitest: KPI formulas, edge cases, data coherence, planted stories, filters, UPC parser, access gate
npm run lint                  # zero warnings allowed
npm run build                 # type-check + production build
npm run test:e2e              # builds a throwaway copy with a one-time password and clicks through it in headless Chrome
```

Node 20 or newer. `npm run test:e2e` needs a local Chrome or Chromium (set `CHROME_PATH` if it is not in the usual place); `SCREENSHOTS=/some/folder npm run test:e2e` also saves one PNG per view. `BASE_URL=https://… E2E_PASSWORD=… node scripts/e2e.mjs` runs the same checks against a deployed URL.

### Environment variables

| Variable | Required | What it is |
|---|---|---|
| `VITE_ACCESS_PASSWORD_HASH` (or `ACCESS_PASSWORD_HASH`) | Yes | Salted SHA-256 hash (64 hex characters) of the demo password. Either name works; `vite.config.ts` passes only this value to the build. Create it with `npm run set-access-password` (local) or set it in Vercel → Project Settings → Environment Variables. **Without a valid value nobody can enter** (the gate fails closed; there is no default password). |

The gate is the UC5 mechanism: only the hash is embedded, the check runs in constant time, and the session ends when the tab closes or with **Lock**. It is a demo barrier, not security: the hash ships in the public bundle, so use a long, unique password and keep the data synthetic. Real protection would need platform-level authentication (for example Vercel Deployment Protection).

### Rules used everywhere

- **Price group first** (Item Group / Price Association): every table starts at the price group (one row per event), drills down to SKU Number and rolls up to Subcategory / Category / Department. Clorox Clean-Up and Clorox Wipes are separate price groups. Whether the price association table keeps history is pending (#13).
- **Gross Sales and Net Customer Sales** are shown separately. The **Sales basis** control (default **Net Customer**) sets the sales used for Promo Sales $, baseline, lift, incremental and margin.
- **Ad week**: Thursday to Wednesday by default, defined once in `AD_WEEK` (`src/data/calendar.ts`) so it stays configurable (#6); holiday exceptions in the ad calendar are not simulated. Fiscal weeks, periods and quarters keep the UC2 Weis 4-4-5 calendar (Sunday to Saturday).
- **Events are included when they start in the selected range**; their metrics use every day of the event. The time filter says so next to the controls ("Promotions starting 08/13/26–11/11/26 (last complete ad week)"); in Rolling mode the **Period** control offers Last 6, 13, 26 or 52 weeks. The baseline window can go back before the selected period; it never changes which promotions you see.
- **Baseline**: average of the N weeks before the event, scaled to the promo days. Proposed defaults (#4): Hot Buy Performance 4 weeks; Other Promo Performance 13 weeks; Promo Run Trend, Promo History and Promo Shopper Impact the default of each event's promo type (Hot Buy 4, TPR / BOGO / Price Lock 13; Other temporary price reduction also 13, the Other Promo Performance default). The user can pick 2, 4, 8, 13 or 52 weeks in any view; the control says "Proposed default, pending confirmation (#4)". Prior promo weeks inside the window are included.
- **Cannibalization**: within the promo window, at **Subcategory** (default, as in the workbook KPI rows), brand, brand-category or category level, items with the same unit of measure, excluding the promoted price group (#3). Measured for the price group, so SKU rows show — with the tooltip "Measured at price group level" (also on the measures built on it: category incremental and net incremental).
- **Cost (#15)**: every item is DC or DSD (`source` in `src/data/products.ts`). DC items use the DC average cost minus scan-downs; DSD items use the replacement cost that day (`src/lib/cost.ts`). Random weight cost is being corrected and meat scope is pending (#15); the tooltips of Promo Units and the margin metrics say so.
- **Vendor promo funding (#7)** is an internal input of Net GM $ and Net Incremental GM $, not a KPI of its own: HQ scan-downs at the expected amount, bill-backs only for DSD items (DC bill-backs are already in the DC cost), no slotting or lump sums, each allowance counted once. A DC scan-down is already in the DC cost (#15), so Net GM $ does not add it again: for DC items Net GM $ adds only other promo allowances. Whether margin metrics stay at all is pending (#7).
- **Every rate is a ratio of totals** and every division is guarded (— instead of an error). Each (ea) and pounds (lb) are never added together.
- Filters a view does not use are greyed out with "Not a filter for this view in the requirements workbook" and never change its numbers.
- **Date range can be typed** (mm/dd/yyyy, Enter or leaving the field) or picked from the calendar. **Paste UPCs**: up to 200 PLUs (4–5 digits), UPC-A (12) or EAN-13 (13) with a valid check digit; invalid and unknown codes are reported back. The popover says it is a concept for review: the functionality to bring to Power BI; the final input format may differ.

## Layout rules

Every view follows these rules. Apply them to any new view or change. All UI text, the README and code comments are in English. `npm run test:e2e` checks rules 1, 2, 4, 5, 6 and 7.

**Rule 1: cascade, from general to particular.** Top to bottom, every view shows:

1. The view title (`SectionHeading`).
2. The key figures (`KeyFigures` tiles with the main KPIs).
3. Charts, from the most general to the most detailed (trends or totals first, breakdowns after).
4. Tables, from the most aggregated to the most detailed (summary first, then the drill-down table).
5. Level 2 sections (`Level2` chip, **Level 2 · not MVP**), always last.

No table comes before a chart of the same view. The view controls (`ViewControls`: baseline window, cannibalization level, sales basis, rows) sit between the title and the tiles as part of the filter bar; the one-line reading of the key figures (`ViewSummary`) and the notices (`BannerStack`, privacy notes) sit right after the tiles. The tabs are the views of the requirements workbook, in its order, without Promo Funding (not part of this dashboard, #2; listed in the KPI definitions dialog). A whole view that is level 2 shows the `Level2` chip next to its title.

| View | Order |
|---|---|
| Hot Buy Performance | Tiles → Daily sales vs. baseline and Category / subcategory bridge → Hot Buy events by price group (hierarchical table) |
| Other Promo Performance | Tiles → Daily sales vs. baseline and Category bridge → Promotions by price group (hierarchical table) → Runs of the same promo |
| Post-Promo Trend (Level 2 tab) | Tiles → Daily units and Daily sales vs. baseline for the selected promo → Post-promo summary by category (events underneath) |
| Promo History | Tiles → Results by fiscal period or week → Sales Lift % and Net Incremental GM $ by Promo Depth Band and by Ad Type / Vehicle → Every past promotion |
| Promo Shopper Impact | Subtabs A / B / C under the title, then per subtab: A tiles → Buyer lift and Promo intensity by category → Category summary (table); B Event dropdown → tiles → Buyers and baskets, Where buyers came from, Multi-item baskets, Also bought → All events (table); C Ad month → tiles (verdicts, average score) → one card per Hot Buy |
| Promo Run Trend | Tiles → Lift across runs and Net Incremental GM $ per run → Each run side by side |

**Rule 2: no business-context block on top.** A view starts with its title and goes straight to the key figures: no eyebrow (priority, "View N of 6"), no user story, no question and no "to validate" text above the content. That information lives in the **KPI definitions** dialog, one entry per view with its priority, question, user story and what is still to validate (with open-question numbers), from `src/lib/viewInfo.ts`. The **Definition pending #N** and **Level 2 · not MVP** chips stay next to each KPI, chart or table (and next to the title when the whole view is pending). `SectionHeading` takes only a title, an optional chip and the objective (rule 4).

**Rule 3: consistency.** The same spacing and the same components in every view: `KeyFigures` tiles, `ChartGrid` / `ChartCard` for charts (each keeps its table view), `HierTable` for tables (each keeps its column chooser and Excel export). Layout changes never change calculations, filters or data.

**Rule 4: the view objective under the title.** Right under each title, one line in the secondary text colour says what the view answers (`objective` in `src/lib/viewInfo.ts`, passed to `SectionHeading`). It is not the user story, which stays in the KPI definitions dialog.

| View | Objective |
|---|---|
| Hot Buy Performance | Did each Hot Buy lift sales and margin above baseline, and how much of that came from other items? |
| Other Promo Performance | Did TPRs, BOGOs, price locks and other temporary price reductions lift sales and margin above baseline, and how much came from other items? |
| Post-Promo Trend | What happens to units and sales in the 4 weeks after a promotion ends (pantry loading). |
| Promo History | Every past promotion for an item or price group, and how results change with discount depth and ad type. |
| Promo Shopper Impact | Did promotions bring more or new shoppers and bigger baskets? Club Card aggregates only. |
| Promo Run Trend | How the same promotion performs from one run to the next, and vs. last year. |

**Rule 5: each control lives next to what it changes.** A control that changes a single block (one chart, one table or one section) sits in that block's header (`BlockSettings`, or `RowsControl` for the table rows). A control that changes several blocks sits in the compact **Calculation settings** bar under the view objective (`ViewControls`), and every block it changes shows its tag (rule 6). A control that changes nothing in a view is not shown there. Every control has an (i) that starts with "Affects: …" and says exactly what it changes; for Cannibalization level the (i) is its "How it works" popover, and its "Definition pending #3" chip sits next to the control. Which blocks each control changes is declared once in `AFFECTS` (`src/lib/settings.ts`) (read from the data each block uses) and drives the bar, the tags and the table below. Promo Run Trend also keeps its "Promotion" selector (which promo type to compare) in the bar: it picks the runs every block shows.

**Rule 6: active-value tag on every block a setting changes.** Each key-figure group, chart or table that depends on a Calculation settings control shows one line of small secondary text with the values it uses ("Baseline 4 wk · Net Customer Sales · Subcategory level"); in chart cards this is the third header row. A value that differs from the view default is shown in the accent colour with its default in brackets ("Baseline 2 wk (default 4)", "Gross Sales (default Net Customer)", "Category level (default Subcategory)"). In code: `<SettingTags block="…" />` in the block header (`KeyFigures` and `ChartCard` take a `tags` prop; table headers use a `block-tags` line). Blocks that no setting changes show no tag, so it is clear at a glance what changed and what did not. Hovering or focusing a tag shows the same "Affects: …" text as its control; the tag's accessible name carries the setting, its value and that text. Tags use theme variables only.

**Rule 8: chart cards.** Every chart uses the shared `ChartCard` header: row 1 the title (at most one underlined term, a small chip such as "Definition pending #3" right after it) and icon-only Excel and Table buttons; row 2 the card's own controls in one line (the "Event" dropdown with its label inside the control, Daily / Weekly); row 3 the active settings line. The subtitle is one short line that identifies the chart, cut with an ellipsis (full text in the tooltip); technical notes go to the chart tooltip or the table view (`tableNote`). Cards side by side reserve the same rows, so titles, controls and plots start at the same height. Spacing uses the `--sp-*` scale (8, 12, 16, 24, 32 px). Axes use round ticks without a leftover ".0" (`niceTicks`, `moneyAxis`), a soft horizontal grid only, and window names (Baseline, Promo, After) in a band above the plot. Change the shared component, not one card.

**Rule 7: glossary.** Key terms use <Term> with a plain-language explanation, once per view. `<Term id="…">` shows the word with a dotted underline (not a link) and opens a popover on hover, keyboard focus or click; Esc or a click outside closes it, and screen readers read the explanation as the term's description. The texts live only in `src/lib/glossary.ts`, and the KPI definitions dialog lists them under "Glossary". Put the term on its first appearance in each view (card titles, subtitles, control labels, tile labels, chips), not on every appearance. `Pending term` and `Level2 term` mark the one chip per view that carries the explanation.

**Items from the prototype review.** The Hot Buy Score (Weis Hot Buy Scoring Framework) and the promo hygiene columns (Promo Hygiene Review thresholds) follow the business method; the Promo Run Trend lift colours are still examples. Change their metrics, weights and thresholds only in `src/lib/scoring.ts`, `src/lib/fatigue.ts` and `src/lib/thresholds.ts` (values only, never the source documents), keep their chips ("Scoring method …", "Promo Hygiene Review thresholds", "Illustrative thresholds", "Proposal for review") and mark new items "Requested in the prototype review" in `src/lib/definitions.ts` (the README tables follow).

**Checks before finishing a change.** Run `npm test`, `npm run lint` (zero warnings), `npm run build` and `npm run test:e2e`; all must pass. The e2e checks rules 1 and 2 in every view; `SCREENSHOTS=./screens npm run test:e2e` saves one PNG per view. Keep the security rules in "Security and hygiene" below.

## Security and hygiene

- No secrets, passwords or keys in the code or the repository; `.env*` files are ignored (except `.env.example`, which has no value).
- No `eval`, `new Function`, `innerHTML` or `dangerouslySetInnerHTML`; all text renders through React.
- Every input is validated and length-capped: URL parameters (unknown values fall back to defaults, `tab=funding` is not a tab and opens the default tab, and the old funding filter parameters are ignored; queries over 2,000 characters are ignored), typed dates, search text, the password (200 characters) and the pasted UPC list (4,000 characters, 200 codes, digits only with a valid check digit). The pasted list is never put in the URL.
- Excel export uses UC2's own dependency-free writer (`src/lib/xlsx.ts`, no npm package); exports guard against spreadsheet formula injection (from UC2).
- Errors show a generic message; details go to the browser console only.
- Strict Content-Security-Policy in `index.html` and `vercel.json` (`self` only; fonts are bundled with `@fontsource`, so nothing loads from a CDN), plus `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS and `noindex`.
- Dependencies are pinned to exact versions from the npm registry (same as UC2, plus `@fontsource/nunito-sans` and `@fontsource/space-mono` 5.3.0). Recommended before a real deployment: generate an SBOM, for example `npx @cyclonedx/cyclonedx-npm --output-file sbom.json`.
